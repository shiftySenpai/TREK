  <action>
Create server/llm-client.js exporting ChatLlmClient class. Per RESEARCH.md § 2, implement:

1. **Constructor:** Accept config object: { provider, model, baseUrl, apiKey, temperature = 0.7 }
   - provider: 'openai' | 'anthropic' | 'local' (local defaults to Ollama at http://localhost:11434/v1)
   - model: model name (e.g., 'gpt-4', 'claude-3-sonnet', 'llama2')
   - baseUrl: optional override for cloud API endpoint or local model server
   - apiKey: optional, required for cloud providers (masked in logs)

2. **chat(messages, options = {}) method:**
   - messages: array of { role, content } (system, user, assistant)
   - options: { temperature, maxTokens = 2048, timeoutMs }
   - Returns: Promise<string> — assistant response content
   - Throws: Error with user-friendly message (no raw API response)

3. **OpenAI-compatible implementation (chatOpenAiCompatible):**
   - Base URL: (this.config.baseUrl ?? 'https://api.openai.com/v1').replace(/\/+$/, '')
   - Endpoint: {base}/chat/completions
   - Headers: Content-Type: application/json, Authorization: Bearer {apiKey} (if provided)
   - Request: { model, messages, temperature, max_tokens: maxTokens }
   - Response: data.choices[0].message.content
   - Timeout: 30s for cloud, 300s for local (detect via baseUrl containing 'localhost' or '127.0.0.1')
   - Error handling: if !res.ok, throw Error with res.status + truncated res.text (200 chars max, no API key)

4. **Anthropic implementation (chatAnthropic):**
   - Base URL: 'https://api.anthropic.com/v1'
   - Endpoint: /messages
   - Headers: Content-Type: application/json, x-api-key: {apiKey}, anthropic-version: 2023-06-01
   - Request: { model, messages, temperature, max_tokens: maxTokens }
   - Response: content[0].text (from first content block)
   - Timeout: 30s
   - Error handling: same as OpenAI (res.status + error message)

5. **getModels() method (placeholder for Phase 1):**
   - Return empty array for now (Phase 2: query Ollama /api/tags or return hardcoded lists)

6. **Use AbortController for timeout:**
   - Create AbortController, set timeout via setTimeout
   - Pass signal to fetch options
   - Clear timeout in finally block (avoid hanging)
   - Per RESEARCH.md: "AbortController for LLM call (30s cloud, 300s local)"

7. **Error mapping (per REQUIREMENTS.md § F5.1):**
   - 429 (rate limit) → "You've sent many. Wait a moment."
   - 408 or timeout → "Request timed out. Check connection."
   - 401 (auth fail) → "API key invalid. Check settings."
   - 503 (overload) → "Model is busy. Retrying..."
   - Other 4xx → "Invalid request: {truncated status message}"
   - 5xx → "Service error. Try again later."
   - Network error → "Connection failed. Check your internet."

Do not throw raw API errors; always wrap in user-friendly message.

1. **Create server/config-resolver.js:**
   Implement resolveConfig(ctx, requestProvider, requestModel) function (per RESEARCH.md § 2).
   
   Fallback chain:
   - If requestProvider and requestModel provided → use those (request override)
   - Else fall back to ctx.config (admin-configured via plugin settings)
   - Else fall back to hardcoded defaults:
     * provider: 'local'
     * model: 'llama2'
     * baseUrl: 'http://localhost:11434/v1'
     * apiKey: ''
   
   Returns object: { provider, model, baseUrl, apiKey, temperature: 0.7 }
   
   For Phase 1, ctx.config expected to be mocked in dev fixtures. Phase 2+ will integrate with addon config resolver.

2. **Update server/index.js — POST /chat handler:**
   
   Handler signature: async handler(req, ctx) {
     const { tripId, message, model, provider } = req.body;
     
     Step A: Validate inputs
     - Ensure tripId is number/string, message is string (max 2000 chars)
     - Return { error: "Invalid input" } if validation fails
     
     Step B: Check trip access
     - Call ctx.trips.getById(tripId) — throws PERMISSION_DENIED if user not member
     - Catch and return { error: "You don't have access to this trip" }
     
     Step C: Resolve LLM config
     - Call resolveConfig(ctx, provider, model)
     - Get baseUrl, apiKey from config
     
     Step D: Load conversation history
     - Query ctx.db: SELECT * FROM messages WHERE trip_id = ? ORDER BY created_at DESC LIMIT 10
     - Reverse to chronological order (newest at end)
     - Format as [{ role: 'user'|'assistant', content }]
     
     Step E: Build LLM request
     - System prompt: "You are a helpful assistant for a trip planning app. Answer questions about travel, destinations, and trip logistics."
     - Add recent history from step D
     - Add user's new message: { role: 'user', content: message }
     
     Step F: Call LLM
     - Instantiate ChatLlmClient(config)
     - Call client.chat(fullMessageArray)
     - Catch errors → return { error: user-friendly message }
     
     Step G: Store messages
     - INSERT INTO messages: user message (role='user', content=message, trip_id=tripId, user_id=req.user.id, created_at=ISO8601)
     - INSERT INTO messages: assistant message (role='assistant', content=response, trip_id=tripId, user_id=null, created_at=ISO8601)
     - Use crypto.randomUUID() for message IDs
     
     Step H: Return response
     - { error: null, response: assistantContent, userMessageId, assistantMessageId }
   }
   
   Logging: Log call details (provider, model, latency) but never log API key or message content in full (truncate to 100 chars if debugging).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Plugin ↔ LLM Provider | Plugin calls external API; must handle auth failures and injection attacks |
| Client Request | User-provided message; must validate length and content before passing to LLM |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | API key in response | Critical | Mitigate | Never return raw API key in response. Mask in error messages. Phase 1 check: grep server/ for "apiKey" in return statements — must find zero. |
| T-02-02 | Information Disclosure | Message content in logs | Medium | Mitigate | Log provider + model + latency, but truncate message to 100 chars for debugging. Never log full user input. |
| T-02-03 | Denial of Service | Uncontrolled message length | Medium | Mitigate | Validate message length max 2000 chars (per REQUIREMENTS.md C3). Return error if exceeded. |
| T-02-04 | Spoofing | Fake LLM response | High | Mitigate | Verify LLM provider authenticity via TLS (fetch enforces HTTPS for cloud endpoints). For local models, ensure baseUrl points to trusted localhost. |
| T-02-05 | Elevation of Privilege | LLM prompt injection | Medium | Mitigate | System prompt is hardcoded (not user-controlled in Phase 1). User message is treated as data, not code. Phase 2: if user can control system prompt, sanitize via template strings (avoid string concatenation). |

</threat_model>
