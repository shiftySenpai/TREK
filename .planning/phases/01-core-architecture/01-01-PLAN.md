<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client ↔ Server | Sandboxed iframe to plugin server via postMessage (trek.invoke bridge) |
| Plugin ↔ Host | RPC communication; host enforces permission checks before allowing ctx.* calls |
| Plugin ↔ Database | Plugin's own SQLite file; no direct access to trip data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | Client ↔ Server bridge | High | Mitigate | trek.invoke() routed via host; host validates user context before calling route handler. Plugin never trusts req headers; user context passed by host only. |
| T-01-02 | Elevation of Privilege | Ungranted permissions in manifest | High | Mitigate | All permissions declared upfront in manifest; host refuses to call ctx.* if not declared. Test early: remove db:read:trips from manifest, attempt ctx.trips.getById() → PERMISSION_DENIED in dev server. |
| T-01-03 | Information Disclosure | API key in logs | Critical | Mitigate | Phase 1 doesn't log requests; Phase 2+: grep codebase for API key patterns before deploying. Never log ctx.config or req.body directly. |
| T-01-04 | Denial of Service | Uncontrolled DB queries | Medium | Accept | Plugin's own SQLite; worst case is plugin crashes. Host will restart it (manifest declares no crash-critical services). Phase 2: add query timeouts if needed. |
| T-01-05 | Tampering | Manifest validation | High | Mitigate | Trek host validates manifest format (via CLI before deployment). Phase 1 checks with `npx trek-plugin-sdk validate`. Invalid manifest → plugin won't load. |

</threat_model>
